# Verification, operation and troubleshooting

Commands below run from the private execution folder generated by step 00.
For a new installation this is `generated/openshift/<region>/<deployment>/`
inside the clone. `internal_doc/` holds private documents, not new execution state.
Numbered launchers automatically select that folder's profile. Diagnostic checks read infrastructure; some save private
logs, reports or certificates. Apply/deploy/approval commands change resources.

## DNS verification

```bash
./05-verify-dns.sh
# Optional polling if publication/cache refresh is pending:
./05-verify-dns.sh --wait 600 --interval 15
```

Focus on **8 PASS, 0 FAIL**: API, internal API, console and a fresh apps wildcard
name must match the registered node IP from both ADMIN and TARGET. Both DNS
answers and OS lookups are checked. A wrong/extra address fails. Bare `dig`
queries root name servers and does not validate the cluster.

After DNS passes, run:

```bash
./00-validate-environment.sh --existing-target
```

Validation is read-only in OCI/on nodes and saves a private report. Exit 0 means
checks pass; 1 means failures; 2 means warnings/unverified evidence. Review warnings;
missing optional client-CIDR evidence is separate from actual cluster readiness.
The validator's generic VM handoff action is already satisfied when this new SCOS
VM exists. Do not create another VM merely because that generic action is printed.

## Installation progress and completion

```bash
./05-wait-for-control-plane.sh --status-only
```

This performs **one read-only snapshot** and returns. Returning to the shell is
not an installation-complete signal. It reports DNS/API readiness, Ready nodes,
operator counts and specific pending conditions for key control-plane services.

```bash
./05-wait-for-control-plane.sh
```

Normal wait streams redacted installer events and shows periodic status updates.
Defaults: 15-second interval after each bounded snapshot, one-hour monitor timeout.
Use `--interval <seconds>` or `--timeout <seconds>` to adjust. Ctrl-C stops only
the monitor, not bootstrap on the VM. The installer also has its own wait deadline.

| Final result | Meaning |
| --- | --- |
| `INSTALLATION NOT READY` | One-shot checks have not all passed; completion is not confirmed. |
| `READINESS SNAPSHOT PASSED` | Snapshot passed; normal installer completion and final acceptance remain. |
| `INSTALLER COMPLETED` | Installer wait succeeded. Run steps 06 and 11. |
| `WAIT FAILED` / `MONITOR TIMEOUT` | Completion is not confirmed; inspect the reported condition or resume monitoring. |

Require these read-only acceptance checks to pass:

```bash
./06-check-control-plane.sh
./11-verify-web-access.sh
```

Step 06 checks API identity, expected node count, Ready nodes, settled operators
and updated machine-config pools. All operators Available is insufficient if
some are still Progressing or Degraded. Step 11 verifies console HTTPS using the
ingress CA and saves private validation artifacts.

## CLI and browser

Source the generated environment before direct CLI commands:

```bash
source ./00-env.sh
oc whoami
oc get nodes -o wide
oc get clusteroperators
oc get machineconfigpools
```

Run direct `oc` commands on the admin host where the selected `KUBECONFIG` exists,
or use the orchestration scripts to execute there. Browser sign-in uses
`kubeadmin` and that cluster's protected `$ADMIN_WORKDIR/sno/auth/kubeadmin-password`.
Use `https://console-openshift-console.apps.<cluster>.<domain>` through the approved
private route/DNS path. These placeholders are not actual deployment addresses.

The optional `08-console-tunnel.sh` creates a SOCKS listener on the invoking
machine. Run it on the browser's machine when a local proxy is required, and
configure proxy-side DNS. A listener on a remote admin VM is not automatically
available on your laptop.

An optional demo changes cluster resources, then verifies HTTPS:

```bash
./07-deploy-demo.sh
./11-verify-web-access.sh --include-demo
```

## Add workers

After control-plane acceptance:

```bash
./09-build-worker-image.sh
./10-import-worker-image.sh
```

These create local media and an OCI custom image. Manually launch one new SCOS
worker from that cluster-specific image first. OL9 is not a registered worker OS
for this workflow. Each node needs a unique hostname, private IP and machine
identity. Never clone a joined node disk or reuse another cluster's Ignition.

Read-only discovery:

```bash
./12-discover-worker-nodes.sh
oc get csr
```

Inspect each CSR identity before individually approving it. Approval changes
cluster state. After intended workers join, update `EXPECTED_NODE_COUNT` in the
private optional profile and repeat step 06. A VM pool may reference the imported
worker image only after a successful individual-node test; pool scaling does not
provide Machine API integration, CSR approval, draining or Kubernetes node cleanup.
Workers do not add control-plane HA.

Base installation does not install persistent storage, MySQL or Submariner.
Configure a suitable CSI/storage layer before stateful workloads. See the
[MySQL workflow](../../mysql-operator/README.md) and the separate
[Submariner workflow](../networking/submariner/README.md).

## Confirmed ISO cleanup

After successful image import:

```bash
./04-cleanup-local-iso.sh
# For imported worker media:
./04-cleanup-local-iso.sh --worker
```

The script verifies the uploaded bytes and AVAILABLE image, lists the local
installer ISO, and requires typing `DELETE`. It deletes only that generated ISO.
Base ISO, cloud image/object, credentials and receipts remain. Do not rerun
build/import merely to monitor an installed cluster after cleanup.

## Bootstrap API and installer diagnostics

Run these commands from the generated execution folder after DNS and environment
validation. Existing checkouts need `git pull` and, for new launchers, a rerun of
`00-create-workspace.sh` from the repository root with the original region and
deployment name/options. This preserves private configuration and installer state.

**Jump host · read-only installation monitoring**

```bash
./05-wait-for-control-plane.sh
```

A successful `/readyz` does not prove authenticated node queries or all operators
are ready. If resource requests repeatedly time out, stop the monitor with Ctrl-C.
Stopping it does not stop installation. Do not repeat image generation or import.

**Jump host · read-only diagnostic collection**

```bash
./05-diagnose-control-plane.sh
```

The script validates the selected kubeconfig/API, workspace domain and single
node's private address. It queries readiness, the authenticated node API, cluster
operators, aggregated API registration and controller-manager installer revisions.
Each request has a 20s timeout with a 35s command limit. It saves a protected JSON
report under the selected admin workspace's `diagnostics/` directory; reports are
private and must not be committed. Exit 0 means evidence collection completed,
not that installation completed. API failures produce a nonzero exit.

Focus on operator Available/Progressing/Degraded conditions, missing aggregated
API CA bundles, and whether a failed installer belongs to the latest revision.
Old failed installer pods can remain after a newer revision succeeds. A localhost
HTTP 403 without credentials only proves the API answered an unauthenticated
request. Compare authenticated direct/tunneled results before changing networking.
Bootstrap API replacement can interrupt requests and delay other controllers;
healthy operators and advancing revisions afterward indicate reconciliation.

**Jump host · conditional controller-manager recovery preview**

```bash
./05-recover-controller-manager.sh
```

Use this only for a latest controller-manager installer that failed with an API
timeout after API access has recovered. A healthy API, Ready matching single node,
Managed controller-manager, and Available/non-Degraded API and etcd operators are
required. A Running, Pending or completed latest installer is not restarted.
If the current revision has already caught up, this is a no-op. Other failure
types are refused. A previous scripted rollout blocks repeated recovery attempts.

**Jump host · conditional cluster change, only after an eligible preview**

```bash
./05-recover-controller-manager.sh --apply
```

This requests a new controller-manager revision through its
`spec.forceRedeploymentReason`, guarded by the resource version checked during
diagnosis. It does not patch certificates, disable TLS, restart the VM or change
networking. It can restart the controller-manager during its rollout. Existing
API-server and etcd configurations are not patched. Keep the private evidence
report and stop on a failed guard; do not bypass the checks.

**Jump host · read-only completion and acceptance**

```bash
./05-wait-for-control-plane.sh
./06-check-control-plane.sh
./11-verify-web-access.sh
```

Wait for `RESULT: INSTALLER COMPLETED`, then require acceptance checks to pass.
See the [controller-manager operator API](https://docs.okd.io/4.21/rest_api/operator_apis/kubecontrollermanager-operator-openshift-io-v1.html)
for the rollout field; its availability does not make every bootstrap failure
eligible for recovery.

## Target host-key recovery

The live installer and installed CoreOS can present different SSH host keys.
An IP reused by a replacement VM can also have a different key. Step 01 refreshes
connection settings but preserves saved identities. DNS polling cannot fix a
changed SSH identity.

For an existing checkout, run `git pull` from the repository root. If the recovery
launcher is missing, rerun `./openshift/community/00-create-workspace.sh --region
<selected-region>` with the same deployment name/options used originally. Return
to the generated execution folder. Stop any DNS poll with Ctrl-C.

These regeneration instructions apply to `generated/openshift/` workspaces.
For a legacy active folder under `internal_doc/`, follow the
[existing deployment guidance](configuration.md#existing-deployments-and-the-new-generated-folder).

Confirm the registered target IP belongs to your intended new VM. This method
trusts the server reached at that address when you accept its replacement key;
it does not independently verify its fingerprint. No console connection is needed.

**Jump host · generated execution folder · read-only preview**

```bash
./05-refresh-target-host-key.sh
```

**Jump host · generated execution folder · local saved-key update and interactive SSH**

```bash
./05-refresh-target-host-key.sh --apply
```

The script backs up the private `known_hosts` file, removes only the registered
target's entries, and reconnects using `StrictHostKeyChecking=ask`. Review the SSH
prompt and type `yes` only if you trust the intended target. It never accepts a
replacement automatically or disables host-key checking. Your private login key
and other saved host identities remain unchanged. If connection fails or you
decline, it reports failure; the target entry has been removed and the backup
remains. Investigate the error before retrying.

**Jump host · generated execution folder · read-only verification and monitoring**

```bash
./05-verify-dns.sh --wait 600
./00-validate-environment.sh --existing-target
./05-wait-for-control-plane.sh
```

Stop on each failure. Recovery changes no VM, DNS, cluster or OCI resources.

### Optional independent fingerprint verification

For stronger identity assurance, obtain the ED25519 fingerprint on the intended
**target VM through its OCI serial console**:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Then on the **jump host**, preview and apply with the console fingerprint:

```bash
read -r -p "Target ED25519 fingerprint from OCI console: " fingerprint
./05-refresh-target-host-key.sh --fingerprint "$fingerprint"
./05-refresh-target-host-key.sh --fingerprint "$fingerprint" --apply
unset fingerprint
```

This optional mode checks the supplied fingerprint and authenticates with the
pinned key before saving it. A mismatch stops recovery without replacing saved
keys. Repeat DNS verification and environment validation afterward.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| NODE_IP requested before media preparation | Use updated preparation scripts. Register the actual address only after manual VM creation. |
| Missing zone after discovery | Discovery saves the view but creates nothing in OCI. Preview, then run explicit DNS `--apply`. |
| CreateZone denied | Verify effective `manage dns-zones`, view-read permission and principal membership in the selected compartment. Keep the OCI request ID; do not switch credentials. |
| GetZoneRecords HTTP 400 | Updated scripts use page size 100. Preserve the existing zone and rerun apply. Invalid parameters do not require wider IAM. |
| OCI records correct but NXDOMAIN persists | Pre-publication negative answers may be cached. DNS polling checks both hosts. Do not promise an exact wait from a single returned TTL. Investigate view/DHCP/forwarding if failures persist. |
| Admin disk too small | Inspect usage. Use confirmed ISO cleanup after import, or expand the correct boot volume/filesystem. Preserve auth/state. |
| Node Ready, installer still waiting | Inspect operator conditions and revisions. Ready node/API alone is not full cluster acceptance. |
| Temporary API refusal during rollout | Check node-side kube-apiserver revision and logs. In a single control plane, replacement/restart can interrupt API access. Distinguish changing revisions from repeated crashes. |
| Authentication/console degraded | Inspect OAuth endpoints, ingress and control-plane discovery/readiness before treating it as a password problem. |
| Some old installer pods Failed | Read their timestamps/logs and compare with current revision/status; historical failures alone do not prove a current stall. |
| Monitor appears silent | Updated monitor streams events and emits snapshots. Stop only the old monitor with Ctrl-C, then rerun it. |
| API readyz passes but reading nodes times out | Resource queries allow 30s per API request and 40s per command; older monitors allowed only 4s. Update and restart monitoring. Continued timeouts need API/resource diagnostics; readiness of one endpoint alone does not confirm completion. |
| Changed SSH host key | Follow [target host-key recovery](#target-host-key-recovery), then repeat DNS and environment validation. |
| OCI scope conflict | Select the correct private profile. Do not copy another cluster's bucket, view, image or node registration. |

References: [private-zone negative caching](https://docs.oracle.com/en-us/iaas/Content/DNS/Tasks/troubleshooting_nxdomain-error.htm),
[OKD single-node monitoring](https://docs.okd.io/latest/installing/installing_sno/install-sno-installing-sno.html).
